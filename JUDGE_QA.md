# Judge Q&A
1. **How do you detect oil spills?** The shipped engine validates an uploaded image and produces a deterministic anomaly-region prototype result. It is not represented as a trained model.
2. **Is the model trained?** No. `PrototypeAnomalyDetector` is an extension point for a future validated segmentation model.
3. **What AIS data is shown?** A local deterministic Demo AIS Dataset, clearly labeled in the UI.
4. **Does the top vessel cause the spill?** No. The score identifies potential relevance for investigation, not proof or attribution.
5. **How is distance calculated?** Haversine great-circle distance from every historical vessel position to the incident; the closest approach is used.
6. **How is time used?** The nearest AIS position time is compared with detection time in a configurable 90-minute window.
7. **How is area calculated?** Detected pixel count multiplied by ground resolution squared, converted to km².
8. **Is area scientifically validated?** Only if valid ground resolution/geospatial metadata is provided. Otherwise it is explicitly Estimated Area based on an assumption.
9. **Why those score weights?** They are visible/configurable prototype policy choices: proximity 0.40, temporal 0.30, type 0.20, trajectory 0.10.
10. **Does vessel type prove anything?** No. It is a low-weight relevance factor, never standalone evidence.
11. **What happens with no nearby vessels?** The API returns an empty ranking and the UI renders an explanatory empty state.
12. **What happens if AIS is disabled?** The system cannot correlate that vessel; the report must state the data gap.
13. **Can you use Sentinel-1?** The detector boundary is intended for this. A production integration needs preprocessing, calibration, model validation, and licensing/data provenance.
14. **Why SAR?** SAR can operate through cloud and at night, but dark signatures have look-alikes and require careful validation.
15. **How are false positives handled?** This prototype labels output as anomaly detection, exposes masks and limitations, and retains operator review status.
16. **How are false negatives handled?** They remain a limitation; production validation and multi-sensor review are required.
17. **Is it real-time?** No. This is a local on-demand prototype.
18. **Does it work without internet?** Yes. UI, dataset, map-style view, APIs, and processing are local.
19. **Why JSON instead of a database?** It keeps the demo portable. The logical entity boundaries map directly to future PostGIS tables.
20. **How is severity determined?** Estimated area is classified against centralized configurable thresholds.
21. **What validates uploads?** Type, payload size, required data URL, coordinates, and ground-resolution constraints in the UI/API.
22. **What data is persisted?** Incidents generated by uploads persist in `data/runtime.json`; Reset Demo restores the seed.
23. **How do you prevent inconsistent cards and tables?** They all request the same canonical incident records from the API.
24. **What is trajectory deviation?** This prototype deliberately does not claim baseline route deviation; it uses a labeled close-approach trajectory signal.
25. **Can an authority use this today?** As a demonstration of triage UX, not as an operational attribution system without data/model validation.
26. **How would you validate it?** Compare against labeled satellite scenes and independently verified incident/AIS records with published precision, recall, uncertainty, and calibration.
27. **How does it scale nationally?** Use object storage, asynchronous jobs, PostGIS spatial indexes, model workers, and authenticated regional access.
28. **Are there security controls?** Local prototype validates request sizes, image types, coordinates, and avoids secrets. Production needs auth, audit, rate limits, malware scanning, and encryption.
29. **What if a vessel spoofs AIS?** That is an explicit evidence limitation; corroborate with radar, satellite, port, and enforcement sources.
30. **What is the future ML roadmap?** Curated labels, SAR/optical preprocessing, segmentation model evaluation, confidence calibration, human review, and model/version provenance.
